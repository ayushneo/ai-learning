# fastapi_uv_template

Same reusable backend skeleton as [`../fastapi_template`](../fastapi_template), with the
packaging layer swapped for **uv** alone — no Poetry, no pyenv. uv handles interpreter
resolution/download, virtualenv creation, dependency resolution, and locking as one tool. The
app code — routes, services, repositories, models, migrations, tests — is untouched; only
packaging changed. Copy this directory to start a new project, delete the `items` resource
once you've read how it's wired, and build your real resources the same shape.

See [`../fastapi_pyenv_template`](../fastapi_pyenv_template) for the sibling variant that
keeps interpreter management (pyenv) and dependency management (pip-tools) as two separate
tools instead — the trade-off table below compares all three.

## File structure

```
fastapi_uv_template/
├── app/                        -- identical to fastapi_template/app, see that README
├── migrations/                  -- Alembic, reads the DB URL from Settings (one source of truth)
├── tests/                        -- AsyncClient + in-memory SQLite, no docker-compose needed to run pytest
├── .python-version                -- uv reads this to pick/download the interpreter; not a pyenv dependency
├── Dockerfile                      -- multi-stage: uv binary + compiler in `builder`, slim `runtime`
├── docker-compose.yml                -- app + Postgres with a healthcheck-gated startup order
├── Makefile                           -- dev/run/test/lint/migrate, thin wrappers over `uv run`
├── pyproject.toml                      -- PEP 621 metadata, no Poetry-specific tables
└── uv.lock                              -- committed, resolved and generated by `uv lock`
```

## Why uv alone (no pyenv, no Poetry)

uv folds three concerns Poetry also bundles — interpreter version, virtualenv, dependency
resolution/locking — into one tool, but implemented as a fast Rust resolver instead of
Poetry's Python one, and reading/writing plain PEP 621 metadata instead of a
`[tool.poetry.*]` dialect. `.python-version` is present here for editor/tooling convention
(pyenv, direnv, IDEs all read it), but nothing in this template requires pyenv to be
installed — `uv sync` downloads a matching CPython itself if the pin isn't already satisfied.

| Concern | Poetry (`fastapi_template`) | pyenv + pip-tools (`fastapi_pyenv_template`) | uv alone (this template) |
|---|---|---|---|
| Interpreter version | Uses whatever `python` it finds, unless you separately install pyenv and `poetry env use $(pyenv which python)`. | pyenv's actual job — `pyenv install`/`pyenv local`, one file, one command, nothing else does this. | `uv sync` reads `.python-version` and downloads a matching CPython itself — no separate tool needed, but also no system-wide "default Python" the way pyenv gives you. |
| Dependency resolution + lock | Own Python resolver, own lockfile format (`poetry.lock`). | `pip-compile` (from pip-tools) resolves `requirements.in` → pinned, hashed `requirements.txt`. Mature, minimal, but a second command to remember to re-run. | Rust resolver, standard `uv.lock`. In this repo, `uv sync --group dev` resolved 57 packages in well under a second cold — noticeably faster than Poetry's resolver on the same set, and no separate compile step like pip-tools. |
| Project metadata | Poetry-specific `[tool.poetry.dependencies]` — needs a Poetry plugin for other tools to read it. | Plain PEP 621 `[project.dependencies]`, or bare `requirements.in` if you skip `pyproject.toml` metadata entirely. | Plain PEP 621 `[project.dependencies]` — any PEP 621-aware tool reads it without translation. |
| Task running | `poetry run <cmd>` | Activate `.venv` then run directly, or `.venv/bin/<cmd>` | `uv run <cmd>` |
| Docker build | Installer script (`curl \| python3 -`) pulls Poetry into the builder stage at build time. | No extra tool needed — `pip install -r requirements.txt` is already in every base image. | `COPY --from=ghcr.io/astral-sh/uv:<pin> /uv /usr/local/bin/uv` — a static binary, no network install step, no interpreter needed to bootstrap the tool. |
| Maturity / ecosystem | Older, widest adoption, most prior art for edge cases (plugin conflicts, private-index auth). | pip + venv are stdlib-adjacent and as old as Python packaging gets; pip-tools is a thin, boring, well-understood layer on top. | Newer (Astral, 2024). Core workflow (sync/lock/run) used here is stable; less prior art than Poetry or pip-tools for advanced cases (workspace monorepos, custom index priorities). |

**Chosen for this variant:** uv alone, because for a template meant to be copied into a new
project, collapsing "which Python" and "which packages" into one command (`uv sync`) is less
for a reader to hold in their head than pyenv-then-pip-tools's two-command handoff — at the
cost of the ecosystem maturity gap in the table above. If you hit a workflow uv doesn't cover
yet, or want interpreter management kept fully separate from dependency locking (e.g. one
pyenv-managed interpreter shared across several pip-tools-locked projects), that's the
concrete case for `fastapi_pyenv_template` or `fastapi_template` instead.

Everything else — layered request flow, models-vs-schemas split, domain exceptions, the
`fastapi-tips` comments in code, the trade-offs on pagination/logging/session-lifetime/tracing
— is identical to `fastapi_template`; see that README, it wasn't duplicated here to avoid the
two copies drifting out of sync.

## Quick start

```bash
cp .env.example .env
uv sync --group dev    # downloads a matching CPython automatically if needed
make migrate      # or: uv run alembic revision --autogenerate -m "init" && make migrate
make dev          # fastapi dev app/main.py -- reload on, http://127.0.0.1:8000/docs
make test
```

Or with Docker (app + Postgres, migrations run automatically before the server starts —
see `scripts/docker-entrypoint.sh`):

```bash
make docker-up
```

## Extending this template

- **New resource**: add `models/foo.py`, `schemas/foo.py`, `repositories/foo.py` (subclass
  `BaseRepository[Foo]`), `services/foo.py`, `api/v1/foo.py`, then one line in `api/v1/router.py`.
  Copy `items.py`'s shape end to end — that's what it's there to demonstrate.
- **New migration**: `make revision m="add foo table"`, review the autogenerated file, `make migrate`.
- **New dependency**: `uv add <package>` (or `uv add --group dev <package>`) — updates
  `pyproject.toml` and `uv.lock` together, same as `poetry add`.
- **Auth**: not included — it's the one piece genuinely specific to each project (session vs. JWT
  vs. OAuth2 provider). Add it as a `Depends()` in `api/deps.py`, following the same pattern as `get_db`.
